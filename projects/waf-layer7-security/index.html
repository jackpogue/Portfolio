Designing safer Layer 7 exceptions for WAF-protected sites

Legitimate administrative traffic could trigger WAF protections, leaving customers to disable their entire firewall or request permanent exceptions. I implemented multiple path-scoped security controls that supported approved customer workflows while keeping the rest of each site protected.

My responsibility
Cross-service security design and implementation through production rollout

Security scope
Layer 7 policy, WAF rules, API validation, edge enforcement, and customer-specific configuration

Environment
Go, OpenAPI, REST APIs, DynamoDB, Cloudflare WAF, custom metadata, microservices, CI/CD, infrastructure automation

The available workarounds weakened security

A control intended to protect a site became a problem when legitimate administrative activity resembled an attack.

GoDaddy’s WAF/CDN platform protected customer applications at the edge. Some administrative requests—particularly during WordPress updates—could trigger protections associated with XSS, SQL injection, file inclusion, or anomaly scoring.

Support could create a permanent exception, but those exceptions accumulated and gradually weakened protection. A customer could instead disable the entire WAF, exposing every application path until someone remembered to turn it back on.

Permanent exception Solves the immediate problem but leaves a broader, long-lived gap in protection.
Disable the WAF Allows the work but exposes the entire application while protection is off.
Path-scoped controls Permit approved administrative workflows while keeping unrelated traffic protected.

Apply least privilege at Layer 7

I implemented multiple administrative WAF bypasses associated with specific, recognized paths and workflows—for example, the WordPress wp-admin area. Only matching traffic to each approved area received its bypass; requests to the remainder of the site continued through normal WAF inspection.

Customers could not submit arbitrary Cloudflare expressions or define unrestricted exceptions. The APIs accepted controlled values, stored them as part of each site’s desired state, and translated them into predefined edge behavior.

IF request path matches the approved administrative path
AND hostname metadata enables that approved path
THEN apply the scoped administrative bypass
ELSE continue normal WAF inspection
Small security boundaries
Each bypass applied only where the approved work occurred.
Controlled input
Schema validation prevented arbitrary edge-policy expressions.
Repeatable enforcement
Desired state produced consistent policies instead of manual configuration.

Edge enforcement Custom WAF rules in development and production zones evaluated the request path and customer metadata.

Make the safer choice easier to use

Overly rigid security controls encourage users to work around them. Broadly permissive exceptions undermine the protection they were intended to preserve. The path-scoped controls supported legitimate customer workflows while limiting each bypass to the smallest practical part of the application.

This is the principle of least privilege applied to application traffic: allow only the behavior required for a specific operation and continue inspecting everything else.
