I explored how internal infrastructure could become a repeatable, on-demand product—from Jenkins deploying Jenkins in Kubernetes to credentials-as-code and Vault-style secret services.

Could internal infrastructure be delivered like a product?

The broader work explored a practical “as-a-Service” idea: make complex operational systems reproducible, testable, and available on demand instead of treating each installation as a one-off environment.

One experiment focused on Jenkins, which coordinated gates, integration tests, dependency updates, cloud-image creation, and releases across a large multi-repository private-cloud product. Testing changes on the production controller meant the tool responsible for protecting releases could itself become the source of release risk.

We created a second Jenkins—nicknamed Leeroy—inside a managed Kubernetes environment. Its job was to test changes to the release platform and deploy or redeploy the production Jenkins service on demand.

Jenkins launched the environment that launched Jenkins

The controller created short-lived Kubernetes agents containing the exact Helm and Kubernetes tooling needed for a deployment. The pipeline checked out the release-platform configuration, prepared environment-specific values and credentials, and installed or upgraded the production service.

That recursive design sounds playful, but it solved a serious problem: infrastructure changes could be reviewed, tested, scheduled, and repeated using the same disciplined pipeline model as product changes.

Replacing the service without losing its memory

Jenkins was disposable; its history was not. I tested pod replacement, Helm deletion, static and dynamic volumes, reclaim behavior, and Deployment versus StatefulSet semantics to verify that a redeployed service reattached to the correct persistent volume and retained its jobs and build history.

Production still needed identity and secrets

The deployment also had to reproduce the parts that make a real service usable: SAML with corporate AD FS, group authorization, TLS, environment-specific Helm configuration, and secrets delivered separately from the shared chart.

Extending the model to credentials as code

A related investigation asked how secret management could become a service rather than a manual handoff. I evaluated HashiCorp Vault and other options for dynamic short-lived credentials, encryption as a service, lease-based access, pluggable storage and authentication, and auditable secret use. Together, these efforts explored a common pattern: encode infrastructure behavior so it can be requested, recreated, and governed consistently.

A deployment platform for the deployment platform Production Jenkins could be launched or redeployed by running a job, while Kubernetes supplied clean agents and persistent storage protected operational history.

Why the broader environment mattered

This was one project inside a larger release-engineering role. The surrounding platform connected many repositories to gating, test clouds, dependency updates, images, releases, and observability. That scale is what made a safe, repeatable control plane valuable.
